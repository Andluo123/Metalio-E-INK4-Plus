# Metalio E-Ink4 Plus：待机退出卡死与复位排查记录

## 问题现象

ESP32-S31 进入待机后，偶发无法退出，随后重启，严重时需要长按电源硬关机再开机。
最初在“开机尚未完成就进入待机，退出后立即再次进入待机”时容易复现；
开机完成后复现概率较低，但排查中正常运行阶段的连续待机也出现过故障。

串口最后通常停在关闭前光、准备浅睡附近，之后没有退出待机日志。
设备浅睡期间 CPU 不执行日志输出，USB Serial/JTAG 也可能断开；
因此单凭串口静默不能判断是否崩溃。USB 恢复枚举期间还可能丢失最早的唤醒或启动日志。

## 定位证据

通过真机自动待机、JTAG 和 RTC 保留区阶段记录，确认失败发生在 SDK 浅睡唤醒路径：

```text
esp_light_sleep_start()
  -> pmu_sleep_start()
  -> pmu_sleep_finish()
  -> rtc_clk_mpll_configure()
  -> 等待 clk_ll_mpll_calibration_is_done()
```

MPLL 校准等待未完成，最终触发 RTC 看门狗系统复位。失败启动记录为
`reset_reason=7`、`raw_cpu0=16 raw_cpu1=16`；这次复位不是任务看门狗触发。
项目校准包装入口的阶段 `501` 表示已准备调用实际校准函数，尚未返回。

失败时保留的寄存器快照示例：

```text
previous_sleep valid=1 cycle=4 phase=501 applied=0xf
sleep regs replay: div=0x249 ctrl=0x248 analog=0x7033 bias=0x707
```

启动时已设置并读回的 DREG/PVT 配置为 `12/12`，失败唤醒校准前却变成了 `7/7`。
这些数字是寄存器配置值。只在启动时设置一次，不能保证后续每次唤醒校准的前提成立。
同时，当前 SDK 的浅睡路径缺少新版实现中的 PSRAM/MPLL 时钟交接处理。

故障点位于 SDK 睡眠函数返回之前，不能据此认定是应用恢复 SD 挂载导致，
也没有证据表明虚拟 U 盘的重新枚举修改是本次复位的原因。

## 最终解决方案

### 代码组织

SDK 兼容修复与 RTC 诊断集中在公共电源目录的 `s31_sleep/` 模块中：

- `s31_sleep.cc`：MPLL 包装、启动配置、RTC 快照和延迟日志重放。
- `s31_sleep.h`：初始化、复位报告、阶段记录和浅睡调用接口；阶段使用具名枚举。
- `s31_sleep_sdk.cmake`：统一接入模块源码、链接包装及构建期 SDK 兼容补丁。

`power_hw.cc` 保留板级电源流程，通过这些接口调用兼容模块，
不直接访问 MPLL 寄存器、SDK 包装状态或 RTC 快照结构。
模块保留原日志标签、阶段值、RTC 布局与寄存器操作顺序。
清空构建目录后会重新生成兼容源码，本机安装的 IDF 不受修改。

### 每次唤醒校准前恢复必要配置

在独立模块 [s31_sleep.cc](../common/power_policy/s31_sleep/s31_sleep.cc) 包装 MPLL 校准入口：

- 仅在 SDK 的 PMU 浅睡恢复路径应用兼容处理。
- 每次校准前恢复 DREG/PVT 为 `12/12`，等待配置稳定。
- 补齐 MPLL 模拟初始化，再执行实际校准，并保存前后寄存器快照。
- 在缓存可能关闭、另一 CPU 暂停的阶段使用 IRAM 和底层寄存器访问，避免日志、分配及跨核锁。
- 睡眠返回后清除作用域标志，避免影响正常运行中的时钟配置。

模拟初始化和启动配置参考 Espressif 官方修复
[fix(mpll): improved mpll calibration flow on esp32s31](https://github.com/espressif/esp-idf/commit/9726078b55430ef8d2ce4a460ebf21d889bb5c12)。
每次唤醒重新恢复配置的处理依据本次真机快照补充。

### 补齐 PSRAM 与 MPLL 时钟交接

[s31_sleep_sdk.cmake](../common/power_policy/s31_sleep/s31_sleep_sdk.cmake) 在构建目录生成 SDK 兼容源码，
不修改本机安装的全局 SDK：

- 入睡前将 PSRAM 时钟切换到 XTAL，并按条件处理 MSPI 时钟，再关闭 MPLL。
- 唤醒后先恢复 MPLL 和 MSPI 时钟，再将 PSRAM 时钟切回 MPLL，之后恢复 PSRAM 访问。
- SDK 已包含对应交接逻辑时跳过该兼容补丁；源码匹配失败时停止构建，要求人工复核。

参考官方当前 [ESP32-S31 PMU 实现](https://github.com/espressif/esp-idf/blob/master/components/esp_hw_support/port/esp32s31/pmu_sleep.c)。
升级 SDK 后应重新核对兼容补丁与包装逻辑，避免重复应用。

### 保留保护与补充日志

RTC 看门狗保持启用，CPU retention 和 PSRAM halfsleep 保持原配置。
关闭这些低功耗功能的对照试验未作为最终方案。

RTC 保留区保存睡眠阶段和寄存器快照；启动时读取上次记录，并在启动后
10、30、60 秒重放，方便 USB 重新枚举后获取复位证据。
阶段 `9` 表示本轮已完成硬件恢复；阶段 `501` 表示即将进入实际 MPLL 校准，
`502` 表示校准已返回。应结合复位原因和后续记录判断，不能只看一条阶段日志。

## 真机验证结果

2026-10-16，修复固件已编译并烧录，同一固件两组自动测试共 **16 轮（6 + 10）全部通过**。
该记录对应模块拆分前的固件；后续结构整理的构建验证不能替代新的真机回归。
模块拆分后已通过完整构建和链接检查，并确认三个 SDK 包装仍位于 IRAM，
两个作用域标志位于 DRAM，32 字节阶段快照位于 RTC NOINIT。
移除临时自动测试后的正式代码也已通过完整构建与链接，尚未重新烧录回归。
保留 RTC 看门狗，启用正常 CPU 掉电恢复和 PSRAM halfsleep。

当时通过临时调试入口执行真实的 5 秒定时浅睡，覆盖：

- 开机初始化尚未结束时立即待机，以及退出后尽快再次待机。
- 后续主页、书架页面的连续待机与恢复。
- 每轮定时唤醒、SD 挂载、访问入口开放、目录读取和壁纸文件读取。
- 唤醒后的串口输出恢复。

每轮检查位均为 `0x1f`。最终读取结果为 `completed=10 failed=0`、
`phase=9`、`bias=0x0c0c0c0c`，并确认 `boot_ready=true`、
`boot_work_active=false`、系统处于 `Idle`。

验证记录位于构建产物 `build/standby-validation-20261016.log`（不随源码保存）。
对应 `Metalio-E-Ink4-Plus.bin` 的 SHA256：

```text
7ae258a7b7eed14a7deec359f263c21e7f9c16e4263e5b428857f778d570e6d1
```

本轮自动测试使用真实定时唤醒，尚未自动验证实体电源键的电气唤醒路径；
16 轮通过也不等同于长期稳定性验证。临时自动测试入口、导航和测试脚本已清理，
正式代码仅保留 RTC 故障快照与日志，不会自动触发待机。

## 蓝牙音频初始化

开机由独立后台任务先复位 BH，再下发模式1配置；复位、电源稳定等待、应答等待和重试均不阻塞主事件循环。
只有收到明确的 `SET MODE 1` 应答才判定就绪，串口写入成功或收到任意数据不代表初始化成功。
首次失败后最多重试3次，每次间隔1秒；同一电源周期重试耗尽后保持失败，不因页面轮询无限重试。
重新上电会使上次确认结果失效。AI、录音测试和老化测试均在后台等待模式确认，再按需申请 I2S 资源。
离开音频功能后释放 I2S 通道与 DMA；蓝牙页面替换数据回调不会移除初始化流程的应答观察者。

初始化失败仅保留失败阶段和尝试次数等必要错误信息；临时原始采样、CRC 和 DMA 周期统计已移除。
当前已完成源文件编译检查及主机模拟回归，尚未验证该初始化流程的整包固件和真机行为。
